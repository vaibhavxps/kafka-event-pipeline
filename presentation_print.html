Problem Statement

The Challenge of Real-Time at Scale

  • 1Monolithic Bottlenecks — Traditional request-response architectures create tight coupling, leading to cascading failures and inability to handle bursty workloads.
  • 2Manual Scaling is Reactive — CPU/Memory-based HPA scaling responds to symptoms, not causes. By the time CPU spikes, thousands of events are already queued.
  • 3Observability Gaps — Without embedded metrics, operators lack real-time visibility into processing throughput, making it impossible to diagnose lag before users are impacted.
  • 4Data Loss Risk — Without durable message storage and proper offset management, transient failures can result in dropped events — unacceptable for critical workloads.
  • 5Operational Complexity — Deploying distributed systems across containers and orchestrators demands a standardized, reproducible infrastructure-as-code approach.

Objectives

What We Set Out to Build

🚀

O1 — Event Producer

Go service generating structured JSON events at 2 events/sec, reliably publishing to Kafka with graceful shutdown.

⚙️

O2 — Event Consumer

Consumer group member processing events with at-least-once delivery guarantees and Prometheus metrics export.

📊

O3 — Observability

Expose kafka_messages_processed_total counter on HTTP endpoint for Prometheus.

🐳

O4 — Containerization

Multi-stage Dockerfiles producing minimal, secure images under 20MB using Alpine with non-root execution.

☸️

O5 — Orchestration

K8s Deployment manifests with health probes, resource limits, init containers, and Prometheus annotations.

📈

O6 — Auto-Scaling

KEDA ScaledObject scaling consumers based on Kafka consumer group lag with threshold of 10 messages.
